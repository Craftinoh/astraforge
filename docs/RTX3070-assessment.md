## Source comparison and engineering conclusions

### RTX 8 GB fork descended from the requested Pareto commit

The exact reference commit is the `neevets/cool_fox` main snapshot `f4b48ad766ddbec1a1867022cd42f7645b0dd55e`. The most relevant accessible descendant is [`grimygunnz/nvidia-3070-VI`](https://github.com/grimygunnz/nvidia-3070-VI), HEAD `58a0c92acc2a72f7c0d186418c7b9ff8c2bd7d94`, GPL-3.0. Its README identifies an RTX 3070 Ti 8 GB / Ryzen 9 5900X / 64 GB host, and its history is nine commits ahead of the Pareto reference. There are no issues or pull requests in that fork; the evidence is in the commit history and its run journal.

The remote manifest pins Rust `1.98.1`, target `x86_64-pc-windows-msvc`, a workspace `diag` profile, and a `diagnostics` feature on the `victory` package. The local build helper's guarded commands match those manifest entries. The fork's `v0.1.0` release has no downloadable assets, so there is no prebuilt executable available through that release. [Pinned toolchain](https://github.com/grimygunnz/nvidia-3070-VI/blob/58a0c92acc2a72f7c0d186418c7b9ff8c2bd7d94/rust-toolchain.toml), [Cargo manifests](https://github.com/grimygunnz/nvidia-3070-VI/blob/58a0c92acc2a72f7c0d186418c7b9ff8c2bd7d94/Cargo.toml), [release](https://github.com/grimygunnz/nvidia-3070-VI/releases/tag/v0.1.0).

Its 2026-11-25/26 Series S report compares the Pareto build at 327 ms/frame (3.1 FPS, 245 ms waiting for the GPU) with the fork's 2,048 MiB title-buffer residency cap plus 64 KiB per-buffer padding at 61.2 ms/frame (16.3 FPS, 0.3 ms waiting, 7.0 GB peak VRAM). A later unchanged-build set reports 58.2â€“59.4 ms/frame, about 17 FPS. These are source-maintainer measurements on a **3070 Ti and 64 GB RAM**, not on this RTX 3070/32 GB host; gameplay frame variation was reported around 5%. They provide a strong candidate baseline and a real limit signal, not a prediction for this machine. Current upstream `main` (`25ff216`) changes only this report; it adds that another refresh-ahead experiment crashed at cutscene start, so refresh remains on the submitting thread. [Current benchmark report](https://github.com/grimygunnz/nvidia-3070-VI/blob/25ff2168267d967c5e428f94726a7384e59cd5b7/docs/nvidia-8gb.md), [fork README](https://github.com/grimygunnz/nvidia-3070-VI/blob/25ff2168267d967c5e428f94726a7384e59cd5b7/README.md), [changes since Pareto](https://github.com/grimygunnz/nvidia-3070-VI/compare/f4b48ad766ddbec1a1867022cd42f7645b0dd55e...25ff2168267d967c5e428f94726a7384e59cd5b7).

The buffer-residency change is backed by the before/after frame times and is enabled by default for DXGI budgets up to 12 GiB. The padding addresses observed `0x887A0006` MMU device losses from shader reads beyond unpadded root-view copies; the report says subsequent runs stopped faulting. These should be retained as a unit. The tested Series X run reached 8,522 MB against a 6,816 MB budget (8.1 FPS, 75.9 ms waiting and 31,000 texture slots waiting), so Series S is the evidence-based 8 GB profile. `VICTORY_DISPLAY_MODE=1920x1080` did not change frame time: the title kept its fixed Series S render size. No source evidence in this fork validates an independent 1280x720 render-scale or own-upscaler variable. [8 GB measurements and visual caveats](https://github.com/grimygunnz/nvidia-3070-VI/blob/58a0c92acc2a72f7c0d186418c7b9ff8c2bd7d94/docs/nvidia-8gb.md).

The most recent profiling still puts the submitting thread at about 55.9 ms of a 58 ms frame while the GPU is idle roughly 21 ms/frame behind it. Thus the current candidate is materially better than Pareto but remains about 1.75Ã— slower than the 33.3 ms budget for 30 FPS. Several later experiments were measured and left off: one-L3 affinity, spinning, and extra worker-thread approaches did not improve the frame; disabling on-demand levels caused device loss. The next code work should target submission/refreshes that copy nothing and card-copy hash/compare passes, with replay and correctness checks. It must not simply discard the remaining unhandled Wave64 heap-defragment shader: the same report identifies that as a real missing dispatch. [Profiling and rejected experiments](https://github.com/grimygunnz/nvidia-3070-VI/blob/58a0c92acc2a72f7c0d186418c7b9ff8c2bd7d94/docs/nvidia-8gb.md).

The fork's guarded launcher clears inherited `VICTORY_*` variables before applying its profile. Its default 46 GiB process cap was tuned on a 64 GiB machine and exceeds this host's 38.35 GiB total commit limit; it must not be copied unchanged. The 2026-11-27 host sample reports 10.05 GiB available commit, below this workspace's 12 GiB start threshold. The game launch path is unset, so no gameplay benchmark can run yet. Recheck commit headroom before launch; do not bypass the guard merely to force a run. The roughly 20 GiB in-world footprint is from another PC and is not a prediction for this host. [Guarded launcher](https://github.com/grimygunnz/nvidia-3070-VI/blob/58a0c92acc2a72f7c0d186418c7b9ff8c2bd7d94/scripts/play-guarded.ps1).

The read-only GitHub check on 2026-11-26 found latest `main` at `25ff2168267d967c5e428f94726a7384e59cd5b7`; its only changed path since the imported snapshot is `docs/nvidia-8gb.md`. The latest CI run (`45880961297`) still fails Clippy with `-D warnings` at `crates/victory-formats/src/texture.rs:1346`: `(i * 7 >> 3)` triggers `clippy::precedence`, which suggests `(i * 7) >> 3`. The behavior-preserving parentheses fix is committed locally as `fe8995b`. The diagnostic build and tests were skipped, and the run published no artifacts. The local launcher and profile files are operational scaffolding, not a renderer build. They retain the audited Series S settings, query hardware and commit headroom before launch, log private/physical/commit memory and per-process dedicated GPU counters, and keep game files, caches and logs outside the repository. Only `VICTORY_TEXTURE_ROOM_PERCENT` differs between the four profiles. None has been benchmarked on this PC, and 720p-to-1080p scaling is not exposed by this source snapshot. The launcher checks that the RTX 3070 is the first DXGI adapter before starting because this source creates its D3D12 device from the default adapter.

### COOL_FOX `f4b48ad766` Pareto-residency

The pinned Windows launcher is a useful baseline for host-memory-safe streaming: it enables deferred/no-wait texture staging, on-demand levels, joined copies, a narrow copy relay, and limited mapping workers. It runs the Series S console profile. Its `residency.rs` is host RAM/commit admission logic; it does not by itself provide a per-process DXGI VRAM budget controller. Those are separate pressure signals and need separate policy in the engine. [Pinned `f4b48ad766` launcher](https://github.com/neevets/cool_fox/commit/f4b48ad766ddbec1a1867022cd42f7645b0dd55e), [residency implementation](https://github.com/neevets/cool_fox/blob/f4b48ad766ddbec1a1867022cd42f7645b0dd55e/crates/victory-gpu/src/residency.rs).

The COOL_FOX source notes and reported timings were measured on Radeon RX 7900 XTX hardware. They are not evidence that its wave-size, mapping-thread, staging, or copy settings improve RTX 3070 frame times. [COOL_FOX findings at the pinned source revision](https://github.com/neevets/cool_fox/blob/f4b48ad766ddbec1a1867022cd42f7645b0dd55e/docs/findings.md).

The NVIDIA-focused derivative carries forward host-memory admission and texture-staging checks, but its results on a higher-memory card do not establish their benefit under the RTX 3070's 8 GB local-memory budget. [NVIDIA-focused source](https://github.com/trustno1-coder/VIctory-NVIDIA).

The shim's advertised console adapter is not the host rendering adapter. The inspected NVIDIA 8 GB branch creates its host D3D12 device on the default DXGI adapter, while this machine enumerates the RTX first. The local probe now records that ordering, but only a runtime device log can confirm VIctory's opened LUID. Windows' DXGI budget is process-specific; exceeding it can page or stall the process, so the engine must query its own `IDXGIAdapter3` budget at runtime. [Microsoft `QueryVideoMemoryInfo`](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo), [budget fields](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/ns-dxgi1_4-dxgi_query_video_memory_info).

The pinned COOL_FOX launcher explicitly sets `VICTORY_AMBIENT_AIR`, `VICTORY_TEXTURE_NO_WAIT`, `VICTORY_RELAY`, `VICTORY_WIDE_BACK`, `VICTORY_JOIN_COPIES`, `VICTORY_INDIRECT_WINDOW`, `VICTORY_CARD_STEPS`, `VICTORY_INDIRECT_BATCH`, `VICTORY_MAP_THREADS`, `VICTORY_THIN`, `VICTORY_JOIN_PARTS`, `VICTORY_UPLOAD_AHEAD`, `VICTORY_LEVELS_ON_DEMAND` and `VICTORY_CARD_BUFFERS_MIN_KB`. It does not set the requested render-scale/upscaler, composition, texture budget/stage, async-submit/present or `SKIP_WC_*` switches. That is a launcher audit only; absent source means I cannot conclude whether an unset variable is unsupported, has a default, or is parsed elsewhere. The RTX 3070 launcher from `victory-unified` exposes a different set of switches, so combining both launchers would not be a valid preset.

`VICTORY_THIN=1` is enabled by the COOL_FOX launcher; the reported blur is from Blackwell. There is no Ampere A/B result in the accessible reports, so keep the value as an explicit 3070 test factor. A different RTX 3070 fork reports that `VICTORY_ASYNC_PRESENT=1` crashed in `nvwgf2umx.dll`, so it stays off in a conservative launch. The unified 3070 launcher also uses a 2,560 MiB texture budget and 64 MiB / 40 ms staging caps; those are build-specific starting points, not COOL_FOX values. [RTX 3070 fork findings](https://github.com/Itsbatt/victory-unified).

### NVIDIA and RTX 3070 evidence

The current `victory-unified` launcher reports RTX 3070 8 GB tuning, but its own README records only about 2+ FPS in normal Release play and a 344 ms outdoor frame on its test system; its long stability run is valuable evidence for descriptor lifetime, not a 30 FPS result. It also records a crash with Series S / FFX_FSR4 on that build and uses Series X. Treat these as fork-specific, self-reported results. [victory-unified](https://github.com/Itsbatt/victory-unified).

The NVIDIA-focused trustno fork uses explicit `VICTORY_ADAPTER`, reports a NaN scrubber for black blobs, and has a Series S half-scale/own-upscaler path. Its strongest public speed figures are on an RTX 5070 12 GB; the maintainer reports that wave-wide translation needs per-program selection because some shaders still blacken water or hang. This is useful implementation history, but not a 3070 FPS prediction. [trustno NVIDIA fork](https://github.com/trustno1-coder/VIctory-NVIDIA).

The 4080 recipe in fxceless issue #1268 reported a 27.2 FPS median on a 16 GB card. Its notes also document major hitching at a 512 MB staging size, long freezes with a 10,000 ms pipeline wait, and artifacts with a small descriptor-buffer minimum. Those values cannot be transplanted to an 8 GB 3070. [RTX 4080 issue #1268](https://github.com/fxceless/victory-fork/issues/1268).

For an 8 GB starting point, `victory-unified`'s 3070 launcher uses a 2,560 MiB texture budget and 64 MiB / 40 ms staging caps, while the separate `victory-nvidia-8gb` fork uses `VICTORY_TEXTURE_DROP_MIPS=2`. These are source-specific starting candidates for later A/B runs. The budget is not a dynamic budget measurement, and dropping two mips is a global quality trade; neither should be installed into another fork before source audit. A 100 ms pipeline wait from one launcher is more defensible for cold-cache experiments than the 10-second wait in the 4080 recipe, but must be tested with that fork's once-only wait logic.

An upstream RTX 3070 report traced a TDR to Wave64 mesh shaders; another patch stopped the hang but left the world black. This makes shader lane translation a correctness gate, not a tuning switch to toggle blindly. [RTX 3070 Wave64 report](https://github.com/Marvisak/VIctory/issues/778).

### Initial 3070 policy

For the imported NVIDIA source, the conservative first run uses its Series S invocation and audited texture streaming defaults. It does not expose a verified 1280x720-to-1080p render-scale setting. The physical GPU reports DXR tier 1.2, but the console title's ray-structure builder and wave64 shader translation are separate runtime issues; hardware RT support alone is not a reason to turn the title's RT path on. Do not set `VICTORY_SKIP_WC_BACK` or `VICTORY_SKIP_WC_COMPARE` without per-scene correctness checks. Keep async present off. Do not copy 4080/5090 values or Blackwell observations directly to Ampere.

Four local profiles are in [launcher-profiles.md](launcher-profiles.md). Their only change from the source's measured Series S settings is `VICTORY_TEXTURE_ROOM_PERCENT` (80/85/90/95), a dynamic local-DXGI-budget share documented and clamped in this source. The launcher validates that source behavior and adapter order before starting. These profiles are candidates only; none has been run in gameplay on this PC.
